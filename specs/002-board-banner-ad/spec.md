## User Scenarios & Testing *(mandatory)*

### User Story 1 - ボード画面の一番下に帯広告が表示される (Priority: P1)

ユーザーがボード（マス目）の画面を開くと、画面の一番下に横長の帯状の広告が1つ表示されます。
広告はマス目や操作ボタンを隠さず、ユーザーはこれまでどおりマスの編集・写真の貼り付け・画像の保存ができます。
広告をタップすると、広告のリンク先が別のタブ（またはブラウザ）で開き、アプリの画面はそのまま残ります。

**Why this priority**: 帯広告を出すことがこの機能の目的そのものです。これだけで提供できます。

**Independent Test**: ボードを1つ開き、画面の一番下に帯広告が表示されること、マス目・ボタンが広告に隠れず
すべて操作できること、広告をタップするとリンク先が別に開いてボード画面が残ることを確かめます。

**Acceptance Scenarios**:

1. **Given** ボードが1つ以上ある状態, **When** ボード画面を開く, **Then** 画面の一番下に帯広告が1つ表示される
2. **Given** ボード画面で帯広告が表示されている, **When** ボードを一番下までスクロールする, **Then** 最後の行のマスやボタンが広告に隠れず、タップして操作できる
3. **Given** ボード画面で帯広告が表示されている, **When** 広告をタップする, **Then** 広告のリンク先が別のタブまたはブラウザで開き、ボード画面と入力中の内容は失われない
4. **Given** ボード一覧・ボードの設定画面・マスの編集シート, **When** その画面を開く, **Then** 帯広告は表示されない

---

### User Story 2 - 広告が保存画像やアプリの動作に影響しない (Priority: P1)

帯広告が表示されていても、ボードを一枚の画像として保存・共有した結果には広告が入りません。
また、通信のない場所でも、広告のせいでボード画面が開けなくなったり、表示が崩れたりしません。

**Why this priority**: 保存画像が画面上のボードと一致すること、オフラインで全機能が使えることは
アプリの中心となる約束であり、広告によって損なってはいけません。

**Independent Test**: 広告が表示されたボードを画像として保存し、画像に広告が含まれないことを確かめます。
通信を切った状態でボード画面を開き、広告以外のすべてが普段どおり使えることを確かめます。

**Acceptance Scenarios**:

1. **Given** 帯広告が表示されたボード画面, **When** ボードを画像として保存・共有する, **Then** 保存された画像に広告は含まれず、広告を出す前と同じ内容になる
2. **Given** 通信のない状態, **When** ボード画面を開く, **Then** 広告が出せない場合でもボード画面は普段どおり表示・操作でき、空の枠やエラー表示は残らない
3. **Given** 広告の読み込みに失敗した、または広告がブロックされた状態, **When** ボード画面を開く, **Then** 広告の場所は詰められ、ボードは広告がないときと同じように使える

---

### Edge Cases

- 画面の高さが低い端末（横向きのスマートフォンなど）では、広告がマス目の大部分を覆ってしまわないか？ → 広告の高さは画面の高さの一定割合以下に抑える（FR-004）
- マスの編集シートやダイアログを開いたとき、広告がその上に重なって操作を邪魔しないか？ → シートやダイアログは広告より手前に表示し、広告はその操作を邪魔しない
- 広告の文字や画像が読み込み途中のとき、ボードの位置がガタつかないか？ → 広告の枠の高さを先に確保し、読み込み後にボードの位置がずれないようにする（広告を出せないと確定した時点で枠を詰める）
- 広告のリンク先を開いたあとアプリに戻ったとき、ボードの内容が消えていないか？ → 入力中の内容を含め、元の状態のまま戻れる

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ボード（マス目）の画面では、画面の一番下に横長の帯広告を1つ表示しなければならない。広告はボードをスクロールしても画面の一番下に表示されたままとする
- **FR-002**: 帯広告はボード画面だけに表示し、ボード一覧、ボードの設定画面、マスの編集シート、画像保存の確認画面などほかの画面には表示してはならない
- **FR-003**: 帯広告は、ボード画面のマス目・達成数・操作ボタンを隠してはならない。ボードを一番下までスクロールしたとき、最後の行のマスと一番下のボタンが広告の上に見えて操作できなければならない
- **FR-004**: 帯広告の高さは、スマートフォン縦画面で画面の高さの 15% 以下、画面の高さが低い端末でも 20% 以下としなければならない
- **FR-005**: 帯広告は、それが広告であることがわかるように「広告」と表示しなければならない
- **FR-006**: 帯広告をタップしたら、リンク先を別のタブまたはブラウザで開かなければならない。アプリの画面・入力中の内容は失われてはならない
- **FR-007**: ボードを一枚の画像として保存・共有するとき、画像に帯広告を含めてはならない
- **FR-008**: 通信がない、広告の読み込みに失敗した、広告がブロックされたなどで広告を出せないときは、広告の枠を詰め、空の枠やエラー表示を残してはならない。この場合もボード画面のすべての機能が普段どおり使えなければならない
- **FR-009**: 広告の読み込みがボード画面の表示を遅らせてはならない。ボードの内容は広告の読み込みを待たずに表示しなければならない
- **FR-010**: 帯広告に表示する内容は、外部の広告配信サービス（Google AdSense など）から取得しなければならない。広告の中身はアプリに同梱しない
- **FR-011**: 帯広告は、ユーザーのボードの項目・写真・タイトルなどの内容を広告の選択や配信のために使ったり、外部へ送ったりしてはならない。広告配信サービスとの通信は広告の表示に必要なものだけとし、ボード画面以外の画面では広告配信サービスと通信してはならない
- **FR-012**: 帯広告には閉じるボタンを設けず、ボード画面を表示している間は常に表示しなければならない（広告を出せないときは FR-008 に従う）
- **FR-013**: 帯広告の枠は、スクリーンリーダーで広告であることがわかるようにしなければならない。キーボード操作でボード画面の操作から広告へ移るとき、ボードの操作ボタンより後の順番にしなければならない
- **FR-014**: 広告配信サービスが Cookie などで利用者の情報を扱うことを、アプリ内から開けるプライバシーポリシーで説明しなければならない。法令や広告配信サービスの規約で利用者の同意が求められる地域では、同意を得るまで広告を表示してはならない

### Key Entities *(include if feature involves data)*

- **帯広告**: ボード画面の一番下に表示する横長の広告。中身とリンク先は外部の広告配信サービスが決め、アプリは枠と「広告」の表示を持つ。ユーザーのボードのデータとは無関係で、ボードのデータにもバックアップファイルにも含まれない

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 通信のある状態でボード画面を開いたとき、帯広告の枠が表示される割合が 95% 以上（広告ブロックを使っている場合、同意を得ていない場合、広告配信サービスが配信する広告を返さなかった場合を除く）
- **SC-002**: 帯広告を追加したあとも、ボード画面を開いてからマス目が表示されるまでの時間が、追加前と比べて 0.1 秒以上遅くならない
- **SC-003**: 帯広告が表示されたボード画面で、すべてのマスと操作ボタンを広告に遮られずにタップできる（幅 360px の縦画面・横画面の両方で確認）
- **SC-004**: 保存した画像に広告が含まれる割合が 0%
- **SC-005**: 通信のない状態で、ボード画面の既存の機能（マスの編集、写真の貼り付け、画像の保存）がすべて広告を出す前と同じように使える
- **SC-006**: ユーザーのボードの項目・写真・タイトルが外部へ送られる件数が 0 件

## Assumptions

- 「ボードのページ」は、1つのボードのマス目を表示・操作する画面（ボード画面）を指し、ボード一覧は含まない
- 「一番下」は、ボード画面の内容の末尾ではなく、スクロールしても画面の下端に表示されたままの帯（スマートフォンアプリでよく見る固定の帯広告）と解釈する
- 帯広告は1画面につき1つだけとし、複数の広告を並べたり、動画・音声付きの広告を出したりはしない
- 広告を非表示にする有料プランや、広告の効果測定（表示回数・タップ数の集計）はこの機能の範囲外とする
- 広告の文言・画像・リンク先は広告配信サービスが決め、アプリの運営者は広告配信サービスのアカウントを用意して審査に通っている
- **前提となる憲章の改定**: 憲章「I. ローカルファースト & プライバシー」は外部との通信を改定なしに導入することを禁じているため、`/speckit-plan` の前に、ボード画面での広告配信サービスとの通信を認める改定（MINOR 以上）を行う。写真やボードの内容を外部へ送らない原則は維持する
- 広告は通信のあるときだけ表示し、オフラインでは表示しない（広告をオフライン用に端末へ保存することはしない）。オフラインで全機能が使える原則（憲章 III）は、広告以外の機能で満たす
- 画面の縦横やサイズに合わせて帯の幅は画面幅いっぱいとし、デスクトップなど幅の広い画面ではボードの幅に合わせる
